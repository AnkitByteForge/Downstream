ADR-015.md

`Commitment` is implemented as a first-class entity with its own table,
repository, and state machine (`OPEN -> PARTIALLY_RELIEVED -> FULLY_RELIEVED`,
or `-> CANCELLED`) — never as a derived attribute computed from
`PurchaseOrder`/`POLine` rows.

Reason:

The Reference Commercial System.md's Recommendation #1, stated as its
first and most important finding: "Model the Commitment as a first-class
object now, not as a derived PO attribute. It is the quantitative impact
surface: committed cost changes before actuals (SAP's predictive
commitment ledger 0E updates at PO save, before any goods receipt)." A
future Downstream Reasoning Pipeline's Impact Analysis stage
(`Downstream_Intelligence_Specification.md` §4, "Commercial Mapping...
CostCode to Commitment/POLine") reasons about committed cost directly —
if `Commitment` were only ever a computed sum over `POLine.value`, that
reasoning would have nowhere real to read from, and the distinction
between "committed" and "actual" (the whole point of the entity) would be
lost.

**CS-1 seeding boundary, recorded explicitly.** A `Commitment` row is
created only where a real cost code is known: `po_4471` (cost code
`23-100`), `po_5201` and `po_5202` (cost code `26-200`). No `Commitment` is
created for `po_4488` or `po_4512` — `docs/05`'s own trace states neither
PO's cost code ("(not stated in trace)" / reached only via graph
dependency), and `Commitment.cost_code_id` is a required field. Inventing
a cost code to manufacture a Commitment row would violate the standing
"do not invent commercial relationships not grounded in the frozen
documents" instruction; the absence is preserved rather than papered over.
