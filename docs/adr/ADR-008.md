ADR-008.md

RES-5 introduces `ScheduleActivity` and `ModelObject` as read-only Reference
Engineering System entities (`The Reference Engineering System.md` §16),
completing the entity list RES-4 (ADR-007) explicitly deferred.

Reason:

**No lifecycle, no mutation API.** Real Primavera/SYNCHRO activities and
model objects are synced *into* an engineering system from scheduling/BIM
tools, not authored through it — mirroring how RES already treats `Vendor`
and `SpecDivision` as read-only reference data. Neither entity gets a status
field or a state machine; both get `GET` list/get only (no POST/PATCH), same
surface shape as `vendors.py`.

**Why ScheduleActivity carries no `status`/lifecycle field.** `The Reference
Engineering System.md` §16 describes "ScheduleActivity (procurement): Submittal
→ Approval → PO → Fabrication → Delivery" — but this is a chain *across*
entities (Submittal's own review status, then Commercial-System states RES
does not own), not a state ScheduleActivity itself transitions through. Per
ADR-007's own precedent ("why drawing incorporation is a relationship, not a
state"), this chain is expressed as a relationship
(`linked_submittal_ids`, realizing `Submittal —SCHEDULED_WITH→ ScheduleActivity`)
rather than collapsed into an entity-local status RES-5 would then have to
invent values for.

**Predecessor/successor as one edge table, not two.** `predecessor_ids` and
`successor_ids` are both named in §16, but storing both directions
independently risks the two lists disagreeing. RES-5 stores one directed
edge table (`schedule_activity_predecessors`: activity → predecessor) and
derives `successor_ids` as its reverse query, guaranteeing the two lists can
never drift apart — a simplification in the same spirit as RES-2's in-memory
pagination (§11.2): correct and simple at this system's scale, not a
fidelity loss the frozen docs require otherwise.

**No `Material` entity — `ScheduleActivity —DELIVERS→ Material` is not
implemented.** No frozen or reference document names `Material` as one of
RES's entities; the closest existing concept is RES-3's `Commitment` (a PO
line pointer). Inventing a new `Material` entity to satisfy one relationship
line would violate the standing "do not invent entities" rule with no
canonical seed data to ground it (`Canonical_Demo_Dataset.md` §21 confirms
`sched_3410` is seeded with no material/delivery detail). Deferred, not
built — flagged here so it is not silently dropped.

**`ModelObject.resource_link` is a direct nullable FK to `ScheduleActivity`,
not a separate `Resource` entity.** `The Reference Engineering System.md`'s
own caveat is explicit that SYNCHRO's 3D object links to a task *through* a
Resource intermediary, and that "the model abstracts both into a generic
`appearance_profile` field," with `resource_link` preserving the nuance as a
single field. RES-5 follows that instruction literally: `resource_link_id`
points straight at `ScheduleActivity.id` (nullable — not every model object
is schedule-linked). No `Resource` entity is introduced.

**No location-adjacency edge on ScheduleActivity.** `Canonical_Demo_Dataset.md`
§13 shows `(Grid B-4)-[location_adjacent, confidence:0.44]->(Schedule Activity 3410)`
— a low-confidence, computed graph edge. Confidence scoring is Downstream's
Reasoning Pipeline's job (`03_Downstream_Systems_Architecture.md`), never
RES's; and `location_id` is not named among ScheduleActivity's §16 fields.
RES-5 therefore does not add a location field to `ScheduleActivity` — the
edge is reproduced only in the Canonical Demo Dataset itself, as a future
Reasoning Pipeline input, not as an RES-owned relationship.

**`sched_3410` seed judgment calls.** The canonical row (§10/§13) gives no
`wbs`, no `type`, and no relationships — its own table marks lifecycle
position "N/A" and value "0". `wbs` is therefore left **nullable** and seeded
`None` rather than invented. `type` has no frozen value either; RES-5 seeds
it `PROCUREMENT` because §16's only lifecycle prose ("ScheduleActivity
(procurement)...") and the row's placement in the Commitments/POs/Delivery
table are the sole contextual signals — an inferred, not literal, choice,
recorded here rather than silently picked.

**`FieldIssue` is explicitly out of RES-5's approved scope.** ADR-007 §"Why
FieldIssue and Commercial change artifacts are deferred" states "FieldIssue
is RES-5" — but the approved RES-5 milestone scope (per the instruction that
opened this milestone) lists only `ScheduleActivity`/`ModelObject`, matching
every other reference to RES-5's scope in this repo
(`IMPLEMENTATION_STATUS.md` §10.9/§12.9, `RES-1_USER_GUIDE.md`,
`docs/engineering/RES_IMPLEMENTATION_CONTEXT.md`'s "RES-5 and Field Issues
remain not started" — treating them as two separate, still-unstarted items).
This ADR records the contradiction rather than silently resolving it:
`FieldIssue` is **not** built in RES-5 and remains fully unscoped for a
future milestone.

Implementation: two dataclasses (`ScheduleActivity`, `ModelObject`) with
closed-vocabulary validation in `__post_init__` (same convention as every
prior RES entity), repository ports supporting `get`/`list_by_project`/`add`
only (no `update` — nothing mutates), and a thin read-only API surface.
