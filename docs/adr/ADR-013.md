ADR-013.md

`POLine.lifecycle_position` is a closed, strictly-sequential five-value
enum: `draft -> issued -> in_fabrication -> shipped -> installed`, lower
case, matching `05_Downstream_Reference_Execution_Trace.md`'s literal
casing choice inside its own JSON payloads' spirit and The Reference
Commercial System.md §M item 3 exactly.

Reason:

This is, per both frozen commercial-domain documents, "the single most
valuable realism feature for demonstrating engineering-to-commercial
impact, because impact severity scales with lifecycle position" (The
Reference Commercial System.md, Recommendation #2). CS-1 implements it as
a real, transition-guarded state machine
(`domain/state_machines/po_line_transitions.py`) — `issue_line`,
`start_fabrication`, `ship`, `install` — each enforcing strict
predecessor-only advancement (no skipping a stage), because severity
reasoning depends on the position being trustworthy, not merely descriptive.

**Casing reconciliation, recorded explicitly.** Two frozen sources disagree
on this vocabulary's case: the product/systems-architecture documents use
lower-case (`draft/issued/in fabrication/shipped/installed`), while
`05_Downstream_Reference_Execution_Trace.md`'s own literal JSON uses
upper-case (`IN_FABRICATION`, `SHIPPED`, `SCHEDULED`, `N/A`) for
`lifecycle_position_at_detection` on Downstream's *Impact* object — a
different object than this system's own `POLine`. Downstream's own
`packages/envelope-schemas` already recorded this exact disagreement and
deliberately left `CommercialArtifactSnapshot.lifecycle_position` as a
free string rather than picking a side (see
`IMPLEMENTATION_STATUS.md` §5.1). This system is a different codebase and
must pick one canonical form for its own storage; it picks the lower-case,
underscore-separated form (`in_fabrication`, not `IN_FABRICATION`),
because that is the literal enum spelled out in The Reference Commercial
System.md itself, the document this system is built from. A future
`connector-sap` adapter is the correct place to normalize casing when
producing a `CommercialArtifactSnapshot` — this system does not attempt
that normalization itself, matching ADR-011's business-key-only boundary.

**`POScheduleLine.delivery_status` is a plain field, not a second state
machine, in CS-1.** The Reference Commercial System.md §E's full Delivery/
GoodsReceipt state machine (Scheduled -> Confirmed/ASN -> In Transit ->
Partially Delivered -> Delivered -> Accepted/Rejected) is CS-3 scope per
the approved plan's milestone table; CS-1's `POScheduleLine.delivery_status`
column exists (the approved plan's §5 schema names it as part of
`POScheduleLine`, which *is* CS-1 scope) but is validated only against a
closed vocabulary at construction time, with no transition functions and
no PATCH endpoint — so CS-3 does not have to migrate free-text data later,
without CS-1 building lifecycle logic for an entity (`Delivery`) it does
not yet own.
