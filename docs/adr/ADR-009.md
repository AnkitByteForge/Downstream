ADR-009.md

The Reference Engineering System exposes an authenticated API surface
through which validated external evidence can create `Drawing` and
`DrawingVersion` engineering records, in `DRAFT` status only. Issuance
remains the existing, unmodified `PATCH .../versions/{id}/issue` endpoint
(RES-4B's `IssueDrawingVersion`) — this ADR adds creation, not a second
issuance path.

Reason:

**Why DIP must use RES APIs, never PostgreSQL directly.** RES owns
engineering-domain truth (`docs/architecture/DSH_Ingestion_Pipeline_Architecture.md`
§0, reconfirmed by the approved DIP -> Engineering Evidence Promotion
plan). A direct DB write from DIP would let DIP's own process construct
`Drawing`/`DrawingVersion` rows RES's application layer never validated —
bypassing the `drawing_version_transitions` state machine, RES's own
project-isolation guards, and every future invariant RES's domain layer
enforces. The API boundary is what keeps "DIP produces evidence, RES owns
truth" true as a runtime property, not just a documented intention. This
mirrors exactly how `connector-procore` is specified to reach RES/Downstream
only through Ingestion & Normalization's API, never a shared database
(`docs/03`'s storage-boundaries table).

**API ownership.** RES's own `application/use_cases/drawing_use_cases.py`
and `api/v1/documents.py` — the same files RES-4B's `IssueDrawingVersion`
already lives in. DIP owns nothing on the RES side; it owns only the HTTP
client that calls this surface (`dip/promote/res_client.py`, E.5).

**Authentication.** RES's existing OAuth2 bearer-token surface
(`OAuthClient` / `OAuthToken` / `IntegrationUser`, `api/v1/oauth.py`,
`api/deps.get_acting_context`'s `kind="integration"` branch) — unchanged
mechanism, not a new one. **One real gap was found and is resolved here,
not silently:** RES's OAuth2 token endpoint currently implements only
`grant_type=authorization_code` and `grant_type=refresh_token`
(`application/use_cases/oauth_use_cases.py`). `docs/04_Downstream_Connector_Layer_Validation.md`
explicitly documents `client_credentials` (2-legged, no user delegation) as
the correct grant for exactly DIP's shape of caller — a headless,
server-to-server batch process with no human to complete an authorization-
code exchange, "matching the server-to-server posture of both real ERPs"
(docs/04, describing the ERPNext/Oracle connector pattern). This ADR
authorizes adding `grant_type=client_credentials` as one additional branch
on the *existing* `POST /oauth/token` endpoint and one additional use case
alongside `IssueTokenFromAuthorizationCode`/`RefreshOAuthToken` in the same
module — an additive completion of RES's own OAuth2 surface to match what
`docs/04` already specifies system-wide, not a second authentication
mechanism. It is implemented as part of E.4, since E.4 is the milestone
that first requires a machine caller to authenticate without a
pre-provisioned authorization code.

**Authorization.** Creation is gated by the same `ctx.require_scope("documents")`
check every existing `documents` PATCH endpoint already uses
(`issue_document_version`) — no new scope concept. DIP's integration
credential is provisioned with `PermissionScope.partial("documents")`,
the same shape Meridian Tower's own seeded "Downstream (partial scope)"
credential already uses.

**Idempotency and duplicate handling.** A retried creation request must
never produce two rows for the same logical resource. Rather than
"checking something approximately" (a pre-query then insert, racy under
concurrent retries), each of `drawings` and `drawing_versions` gets a
database-level UNIQUE constraint on its natural key —
`(project_id, sheet_number)` for `drawings`, `(drawing_id, revision_label)`
for `drawing_versions`. `CreateDrawing`/`CreateDrawingVersion` attempt the
insert and, on a unique-constraint violation, fetch and return the
existing row instead of raising — a real upsert, enforced by the database
itself, not by application-level best-effort checking. This is the
deterministic-identity requirement the promotion orchestrator (E.6) relies
on.

**Provenance pointer strategy.** RES stores exactly one new, additive,
nullable field: `RevisionCloud.source_evidence_ref: str | None` (E.3) — an
**opaque** string. RES never parses, validates the shape of, or derives
meaning from this value; it is a pointer DIP alone knows how to resolve
back into full evidence (document, page, bounding box, OCR engine,
confidence). This is the same "pointer, never a copy" discipline
`docs/03`'s storage-boundaries table already requires of
`raw_document_ref` — extended one hop earlier, to DIP.

**No full OCR/evidence JSON stored in RES; no Equipment entity.** RES's
schema gains one string column. It does not gain OCR word boxes, bounding
boxes, confidence scores, or any DIP-internal type. `Equipment`/
`EquipmentTag` was deliberately never introduced as an RES entity in
RES-4 (ADR-007) or RES-5 (ADR-008, which declined the analogous `Material`
entity for the identical reason: no frozen source names it). This ADR does
not revisit that decision. A promoted E0.4 row's equipment identity exists
in RES only as free text inside a `RevisionCloud.description` and its own
`source_evidence_ref` pointer back to DIP — never as a queryable RES
entity. If a future milestone genuinely needs equipment as a first-class,
cross-drawing RES concept, that requires its own ADR; this one does not
authorize it.

**Auditability.** Every creation is a normal RES-owned row, subject to
RES's existing audit posture (the same as every other entity — no new
audit mechanism). The *promotion attempt* itself (did DIP successfully
call this API, when, with what result) is DIP's own audit concern, tracked
in DIP's promotion-attempt log (E.6), not duplicated into RES.

**Retry/failure behavior.** RES's side of this is stateless and ordinary:
a valid request either succeeds (200/201, existing or newly-created row)
or fails with a normal HTTP error (400 malformed body, 404 unknown
project, 409 only for a genuine domain-rule violation distinct from the
idempotent-duplicate case, which returns 200 with the existing resource,
not an error). RES does not implement retry logic itself — retry/backoff
is the caller's (DIP's) responsibility, per E.6.

**Backward compatibility.** `source_evidence_ref` is nullable; every
existing `RevisionCloud` row (Meridian Tower's real RFI-214/DWG-E-1.1
data) is unaffected and continues to read/serialize with `None`. The new
POST endpoints are additive routes; no existing route's request/response
shape changes. The new UNIQUE constraints must be validated against
Meridian Tower's existing seeded `(project_id, sheet_number)` and
`(drawing_id, revision_label)` pairs before the migration is considered
safe (verified in E.4, since no existing seed data is expected to
collide — Meridian Tower's sheet numbers and revision labels are already
unique per drawing by construction of the seed script).

**Security.** No secrets are introduced by this ADR — DIP's OAuth client
secret is provisioned the same way Meridian Tower's existing integration
credentials are (seeded, hashed at rest via the existing `PasswordHasherPort`,
never stored or logged in plaintext). `docs/04`'s least-privilege posture is
followed: DIP's credential is scoped to `documents` only, never `full`.

Consequences:

- RES gains its first genuine external-write surface. Every other entity
  remains read-only-via-API (mutated only through its own specific
  lifecycle PATCH endpoints, or the existing seed script) — this ADR does
  not generalize creation to any other entity type.
- `drawings`/`drawing_versions` gain UNIQUE constraints they did not
  previously have. This is a real, if low-risk, schema tightening;
  verified against existing seed data before the migration ships (E.4).
- RES's OAuth2 surface gains a `client_credentials` grant, additive to the
  existing two grants.
- DIP becomes a second, real caller of RES's API surface (the first being
  the human frontend and Meridian Tower's own seeded Downstream
  credentials) — proving the "swap the mock for real Procore is a
  configuration change" claim (`docs/architecture/DSH_Ingestion_Pipeline_Architecture.md`
  §3-M) for the first time with a second, independent caller.

Alternatives considered:

- **DIP writes to RES's PostgreSQL directly.** Rejected — this is the one
  option the mission's own "DIP must not become a second engineering
  application" / "RES owns engineering-domain truth" rules exist to
  foreclose; it would let a DIP schema change or bug corrupt RES state
  with none of RES's own domain validation ever running.
- **Application-level idempotency check (query-then-insert) instead of a
  DB constraint.** Rejected — race-prone under concurrent/retried
  requests, and the "deterministic identity, not something approximate"
  requirement this milestone was explicitly given rules it out.
  A DB-level UNIQUE constraint is what actually makes duplication
  impossible, not merely unlikely.
- **Reuse the existing `authorization_code` grant for DIP** (seed a
  single-use code, as Meridian Tower's own Downstream credentials already
  do). Rejected as the primary mechanism — `authorization_code` models a
  human-delegated, one-time connect step; DIP is a recurring, unattended
  batch job with no human present to complete that exchange each run, and
  `docs/04` already names `client_credentials` as the correct shape for
  this exact caller profile.
- **A generic `EngineeringFact`/property-bag entity to hold promoted
  values instead of free-text `RevisionCloud.description`.** Rejected —
  this is exactly the "Equipment" question by another name; no frozen
  source names such an entity, and RES-5/ADR-008 already declined the
  analogous move for `Material` on identical grounds.
