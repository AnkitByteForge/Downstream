Bookmarks/outline are the single best provenance source for docs 02/03 — nearly every sheet has exactly one bookmark whose title string already contains <sheet number> - <sheet title> (e.g. "E0.4 - AIR HANDLER REPLACEMENT SCHEDULE"), and it maps directly to a page index via get_dest(). Verified this matches the in-page title-block text exactly (cross-checked page 371/373/375).

Docs 01/04 have no per-section bookmarks, but every spec page carries a self-describing footer present on literally every page, e.g.:AIR HANDLING UNITS09/29/2023 23 74 13 - 5 DGS000000142452

<section title> / <date> <section number> - <page-within-section> <project number>. This is a highly reliable, regex-extractable per-page anchor (\d{2} \d{2} \d{2} - \d+ DGS\d+) for building the SpecSection → page range structure — more reliable than reconciling the human-readable Table of Contents' internal page numbers against PDF page indices.

Title blocks are text-extractable on all drawing sheets sampled (project name, sheet number, date, engineer stamp block) — confirmed on doc02 p.0, p.371, p.373, p.375.

Tables/schedules survive text extraction inconsistently — this is the central finding of Phase 1, with three distinct failure/success modes found:

Native text schedule — doc01's spec-book equipment tag lists (e.g. p.324: "Units Tagged: AHU-1,2,3...20"). Fully extractable, no issue.

Raster-image schedule embedded in a vector sheet — doc02 p.373 (E0.4, AHU schedule): confirmed by object inspection — 1 image covering 36.9% of the page, only 126 native text objects (all title-block boilerplate). Doc02 p.375 (E0.6, panel schedules): 13 images covering 51.9% of the page. The actual MCA/MOCP/FLA/breaker values are pixels, not text.

Text-drawn-as-vector-curves — doc03 pages 36, 43, 44, 45, 53 (the mechanical/electrical schedule and single-line-diagram sheets): near-zero native text (372–462 chars, title block only), near-zero raster coverage (~0.5%), but 19,000–41,000 vector PATH objects per page. Rendered and visually confirmed (see §5) — these are legible, crisp CAD-plotted diagrams/tables, but the text was flattened to outline geometry at plot time (a common Bluebeam/AutoCAD plot-driver artifact), so it is invisible to any text-layer extraction method, identical in symptom to a raster scan even though it isn't one. Doc01's "List of Drawings" section (13 pages) has the identical signature (916 PATH objects, 0 text, 0 images) — confirmed by rendering (§5).

No pages appear to be genuine scanned/photographed raster documents (i.e., a phone/scanner capture of a paper page). Every "no extractable text" page investigated turned out to be either an embedded raster table-image or vector-curve artwork, both born-digital, both crisp at render time — good news for OCR accuracy expectations (no scan noise/skew to fight).

New, to be added only with explicit approval:

An OCR engine for the flagged pages only. Two real options with a genuine tradeoff to flag: Tesseract via pytesseract (industry-standard, but requires installing the separate Tesseract binary on the machine — a system-level dependency, not pure pip, and a real friction point on Windows) vs. a pure-pip OCR (e.g. rapidocr-onnxruntime or easyocr) that installs cleanly via pip with no external binary but is a heavier dependency and less battle-tested for dense technical-drawing text. Recommend prototyping both on 2–3 pages before deciding.

No vector DB, no bulk-LLM summarization — explicitly out of scope per your instructions, and nothing in this reconnaissance suggests they're needed for the stated goal (selective, provenance-preserving extraction, not semantic search over prose).
